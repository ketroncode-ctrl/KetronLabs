KC Editor & Ovius Developer Documentation

Introduction

KC Editor (Ketron Code Editor) is a premium, lightweight, local-first Agentic IDE built for developers who demand high performance without heavy hardware constraints.

Traditional IDEs are heavily bloated with background diagnostics, package caches, and telemetry that degrade execution on entry-level systems. KC Editor is engineered from the ground up to run seamlessly even on systems with 4 GB of RAM. It manages this efficiency by running core UI and shell operations natively and deploying remote execution loops only when needed.

Founded in 2024 by Rithish, Ketron Labs operates on the core principle that technology should be simple, powerful, and accessible to everyone. Our mission is to democratize software development by eliminating the dependency on expensive, high-end hardware, enabling students, beginners, and professional developers alike to build state-of-the-art applications on standard machines.

Core Ideology

The system is built on a "local-first, hybrid sandbox" ideology. All files are stored, compiled, and audited locally on your machine. External network cycles are reserved exclusively for AI completions via direct APIs.

Product Ecosystem

Ketron Labs is building a unified software ecosystem bridging local development, browsing, and knowledge management.

The Ketron Labs ecosystem integrates three primary pillars designed to cover the full lifecycle of software creation and information management:

  • Ketron Code Editor (KC Editor): The central developer engine designed to run seamlessly on low-resource machines, complete with built-in P2P collaboration (KC Connect) and autonomous AI agent subsystems (Pilot Mode).
  • Ovius Browser & Ovius Pulse: A developer-centric web browser that directly embeds visual prototyping utilities. Instead of constantly context-switching between code editors, terminals, and external browser viewports, Ovius bridges the gap. Its flagship visual builder, Ovius Pulse, allows developers to visually modify website elements on a live canvas and synchronize edits directly back into the editor's code buffer.
  • Ovi Memory (Upcoming): Currently in active development, Ovi Memory is an intelligent personal knowledge base system. It addresses a major developer pain point: information fragmentation. Rather than scattering bookmarks, design files, notes, snippets, and project ideas across separate applications, Ovi Memory provides a central, AI-powered storage node that organizes and instantly retrieves knowledge.

Seamless Integration

These products are built to share underlying protocols, enabling direct communication between browser canvases, local files, and knowledge caches without the overhead of heavy background processes.

Architecture

A hybrid container blending native python layout management with robust .NET CLR WebView2 integration.

KC Editor uses Python (Tkinter) for window frame handling, configuration diagnostics, file system access, and subprocess spawning. To run the Monaco Editor canvas and Ovius Pulse previews without spawning resource-heavy external chromium windows, it embeds an Edge WebView2 container parented directly inside the Tkinter frame layout using native Win32 window handles.

The editor utilizes pythonnet (clr) to load the native .NET System.Windows.Forms framework, instantiating a WinForms Control that parent-wraps the pywebview EdgeChrome webview. Using the Win32 API via Python's ctypes module, the webview window handle (chwnd) is parented directly to the Tkinter frame. This creates a zero-overhead window nesting hierarchy.

Python (Win32 parenting patterns in ketron.py) 
# Excerpt of the Win32 reparenting sequence used in WizardWebView
def _ensure_parenting(self):
    import ctypes
    user32 = ctypes.windll.user32
    expected_parent = self.winfo_id() # Tkinter Frame Handle
    current_parent = user32.GetParent(self.chwnd)
    
    if current_parent != expected_parent:
        # Bind child handle directly to Tkinter parent
        user32.SetParent(self.chwnd, expected_parent)

        GWL_STYLE = -16
        WS_CHILD = 0x40000000
        WS_POPUP = 0x80000000
        WS_VISIBLE = 0x10000000
        
        # Adjust style flags to remove POPUP borders and make it a visible CHILD window
        style = user32.GetWindowLongW(self.chwnd, GWL_STYLE)
        style = (style | WS_CHILD | WS_VISIBLE) & ~WS_POPUP
        user32.SetWindowLongW(self.chwnd, GWL_STYLE, style)

        # Enable WS_CLIPCHILDREN recursively to prevent GUI rendering flicker
        WS_CLIPCHILDREN = 0x02000000
        curr = expected_parent
        while curr:
            parent_style = user32.GetWindowLongW(curr, GWL_STYLE)
            user32.SetWindowLongW(curr, GWL_STYLE, parent_style | WS_CLIPCHILDREN)
            curr = user32.GetParent(curr)

        # Flush frame modifications to apply new window parameters
        SWP_FRAMECHANGED = 0x0020
        SWP_NOMOVE = 0x0002
        SWP_NOSIZE = 0x0001
        SWP_NOZORDER = 0x0004
        SWP_NOACTIVATE = 0x0010
        user32.SetWindowPos(self.chwnd, 0, 0, 0, 0, 0,
                            SWP_FRAMECHANGED | SWP_NOMOVE | SWP_NOSIZE | SWP_NOZORDER | SWP_NOACTIVATE)

To support responsive scaling, the Tkinter frame intercepts window geometry events via a <Configure> binding, calling the Win32 MoveWindow function to continuously fit the parented WebView2 control to the target layout frame coordinates.

Portable Environment

KC Editor ships with a self-contained runtime environment to ensure maximum stability and zero-configuration setups.

A major friction point for new developers is establishing interpreter paths, setting environment variables, and downloading secondary packages. Beginners and students using entry-level laptops often get blocked by path conflicts or installation issues. KC Editor solves this by shipping a fully self-contained portable Python runtime within the editor's installation directory. The editor isolates all runtime processes to this local directory:

No Interpreter Conflicts

The compiler and terminal commands spawn scripts specifically referencing the local interpreter. This ensures that even if you have existing Python interpreters, virtual environments, or system paths, KC Editor execution routines remain fully isolated and won't conflict with or affect your main operating system configurations.

Pilot Mode Loop

Pilot Mode operates in an autonomous developer loop to write, run, and self-correct files until goals are met.

When the developer triggers Pilot Mode, the AI agent performs a structured, multi-phase execution process:

Phase 01: Analyze & Plan

Reads the directory structure, loads relevant file contexts, maps internal dependencies, and draws up a structured Implementation Plan (saved to the workspace).

Phase 02: Write & Edit

Surgically edits the files, patching lines of code and inserting new modules without disrupting unrelated code elements.

Phase 03: Test & Self-Debug

Automatically triggers execution commands in the background. If compilation errors, traceback logs, or testing assertion failures are encountered, Pilot captures these errors, analyzes them, and recursively loops back to edit the code until all assertions pass.

Gemini REST Integration

Engineered to bypass bulky SDK packages by interacting directly with the Gemini REST API.

To keep the IDE lightweight and easy to distribute, the codebase handles all model requests using standard Python network libraries (urllib.request, urllib.parse, and json) directly interfacing with Google Generative Language REST endpoints. There are no secondary library dependencies like google-generativeai, reducing the app's overall memory footprint.

Python (API handler in ketron.py) 
def _gemini_rest_request(api_key, path, payload=None, timeout=20, method="POST"):
    import urllib.request
    import urllib.parse
    import json
    
    query = urllib.parse.urlencode({"key": api_key})
    url = f"https://generativelanguage.googleapis.com/v1beta{path}?{query}"
    
    headers = {"Content-Type": "application/json"}
    data = json.dumps(payload).encode("utf-8") if payload else None
    
    request = urllib.request.Request(url, data=data, headers=headers, method=method)
    with urllib.request.urlopen(request, timeout=timeout) as response:
        return json.loads(response.read().decode("utf-8"))

The editor falls back through a sequence of flash models (e.g., gemini-2.5-flash, gemini-2.0-flash, gemini-1.5-flash) to guarantee low latency. User configurations are saved locally in the user profile directory under ~/.ketron_ai_config.json.

Ovius Pulse Visual Builder

Ovius Pulse is a visual canvas builder bundled inside the editor, facilitating rapid layout prototyping.

When the Ovius Pulse workspace is opened, the editor retrieves the active HTML file, analyzes its markup, and launches a visual drag-and-drop workspace in an embedded WebView2 container. To render relative file-based files properly inside the sandbox, Ovius Pulse executes several pre-rendering routines:

Python (Asset Parser in ketron.py) 
# How Ovius Pulse maps and inlines resources before loading html in the WebView
def _ovius_build_payload():
    html_path, html = _ovius_html_candidates()
    payload = {"html": html, "filePath": html_path, "baseUrl": "", "styles": [], "scripts": [], "assets": {}}
    base_dir = os.path.dirname(os.path.abspath(html_path))
    payload["baseUrl"] = "file:" + urllib.request.pathname2url(base_dir) + "/"
    
    # Parse and inline external stylesheets
    for m in re.finditer(r'<link[^>]*rel=["']stylesheet["'][^>]*>', html, re.I):
        href = re.search(r'href=["']([^"']+)["']', m.group(0), re.I).group(1)
        local_path = os.path.normpath(os.path.join(base_dir, href))
        if os.path.exists(local_path):
            with open(local_path, "r", encoding="utf-8") as f:
                payload["styles"].append({"css": f.read()})
                
    # Rewrite relative assets (e.g. image src) to absolute file:// URLs
    for m in re.finditer(r'(?:src|href|poster|data-src)=["']([^"']+)["']', html, re.I):
        val = m.group(1)
        if not val.startswith(("http://", "https://", "//", "data:")):
            abs_url = "file:" + urllib.request.pathname2url(os.path.abspath(os.path.join(base_dir, val)))
            payload["assets"][val] = abs_url
    return payload

Asset Rewriting & Path Resolution

All relative paths inside HTML tags (such as <img src="img.png">) are parsed and converted to absolute file:// URLs so assets render correctly inside the sandboxed iframe container.

Styles & Script Inlining

Linked external stylesheets and custom JS files are read from the disk and dynamically injected inline inside the visual canvas sandbox, maintaining styles without launching local servers.

Bidirectional Sync

The editor maintains Monaco as the single source of truth, syncing edits dynamically back and forth.

To avoid race conditions and file-conflict states, KC Editor manages synchronization using an asynchronous queue with minimal diff updates:

Python (Difference Engine in ketron.py) 
# SequenceMatcher is used to isolate changes and run a single applyEdit inside Monaco
import difflib
sm = difflib.SequenceMatcher(None, old_html, new_html, autojunk=False)
opcodes = sm.get_opcodes()
changes = [(i1, i2, j1, j2) for tag, i1, i2, j1, j2 in opcodes if tag != 'equal']

if changes:
    first_diff = changes[0][0]
    last_diff = max(c[1] for c in changes)
    new_start = changes[0][2]
    new_end = max(c[3] for c in changes)
    
    new_span = new_html[new_start:new_end]
    sl, sc = to_linecol(old_html, first_diff)
    el, ec = to_linecol(old_html, last_diff)
    
    # Apply edit to Monaco atomically, preserving cursor and history
    editor.apply_edit(sl, sc, el, ec, new_span)

Minimal-Span Diffing Algorithm

When you edit elements on the Ovius Pulse visual canvas, the visual builder serializes the updated DOM and sends the text back to Python. Python diffs the new DOM against the Monaco document buffer. For documents under 15,000 characters, it calculates the smallest span of character changes and performs a single atomic transaction inside Monaco. This ensures that the developer's cursor position, scroll state, and undo stack history remain completely unaffected. Larger documents bypass diffing and undergo full replacement to protect GUI responsiveness.

Conversely, text edits in Monaco automatically trigger a modification hook. It runs a debounced timer (400ms delay). Once the timer expires, it calls the webview bridge's sourceChanged message, pushing changes directly back to update the Ovius Pulse preview canvas instantly. If a sync from the visual builder is already pending, reverse sync is paused to avoid circular conflicts.

Direct Web Deployment

Publish visual prototypes instantly using native Vercel and Surge integration.

Ovius Pulse features built-in publishing options that export and host your web layouts directly to live servers, bypassing manual command-line builds:

  • Vercel REST Deployment: The editor connects directly to the Vercel Deployments API (https://api.vercel.com/v13/deployments). If a user token is provided, Python packages the DOM assets, encodes the index.html payload in UTF-8, and POSTs the request using standard generative REST request handlers. The deployment runs on a background daemon thread so the editor UI never blocks.
  • Surge Fallback Deployment: If Vercel credentials are omitted, the editor deploys to Surge as a fallback. It automatically generates unique Surge credentials locally by querying and hashing the host machine's MAC address (uuid.getnode()), creating an account profile: ovius-user-<mac_hash>@outlook.com. The build engine writes the HTML to a temporary directory, handles automated credentials authentication via standard IO stdin piping, and triggers npx -y surge as a background subprocess.

new_email = f"ovius-user-{mac_hash}@outlook.com"

Deployment Configuration Storage

Surge credentials are saved in the user home directory at ~/.ovius_surge_config.json, while site subdomains are persisted in the active workspace root directory inside .ovius_project.json to ensure layout domain consistency across updates.

KC Connect (Real-Time Collaboration)

A peer-to-peer real-time collaborative workspace enabling multiple developers to build together.

KC Connect is the real-time collaboration engine built natively into KC Editor. It allows multiple developers to join a single shared coding session to read and edit project files concurrently:

Real-Time Synchronization

Edits, selection coordinates, and cursor states are synchronized instantly across connection lines. The engine broadcasts events through local network ports, updating editor contents with visual cursor followers for every active collaborator.

In-App Communication

Collaborators can communicate directly inside the workspace window via built-in developer chat, ensuring teams align on tasks and implementation plans without leaving the coding interface.

Integrated Terminal

Run compilers, execute tests, and manage system operations directly from the editor canvas.

KC Editor includes an integrated terminal emulator that interacts directly with your operating system's shell (e.g. Powershell, CMD on Windows, or zsh, bash on macOS/Linux):

Subprocess Spawning & Output Streaming

When you run code or enter a shell command, the terminal module spawns isolated subprocesses, streams stdout and stderr output in real time to the terminal canvas, and monitors exit codes to feed debugger processes.

Firewall & Networking

Diagnostics tools built to audit network parameters and ensure local collaboration pathways remain clear.

For collaborative development operations, KC Editor contains network probing blocks that establish connection parameters and test local port states. These processes are guided by local user profile configurations:

  • Welcome Flag: ~/AppData/Local/KetronCodeEditor/welcome_seen.json verifies if the welcome wizard has run.
  • Firewall Permissions: ~/AppData/Local/KetronCodeEditor/firewall_permission.json audits attempts to open local socket endpoints, alerting developers if OS firewalls block collaboration ports.

Win32 Captions & Themes

Premium layout elements customization incorporating native Win32 API calls.

To deliver a premium, native feel on Windows OS, the editor implements immersive theme customization hooks. It directly calls functions from Windows system DLLs (dwmapi.dll and user32.dll) using Python's built-in ctypes module. This bypasses the default OS title decorator limits, applying a custom dark caption style onto top-level Tkinter and WinForms frames:
